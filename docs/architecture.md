# AI-интервьюер — архитектура

Статус: описывает то, что построено, 2026-09-04. Решения из `decisions.md`
считаются входными.

Документ обновляется вслед за кодом. Если расходится — прав код, а расхождение
считается ошибкой этого файла.

## 1. Топология

Всё поднимается одним `docker compose up`.

```
                    ┌─────────────┐
   браузер ───────► │  frontend   │  nginx + React SPA
                    └──────┬──────┘
                           │ REST + presigned URL
                    ┌──────▼──────────────────────────┐
                    │          backend                │  Spring Boot / Kotlin
                    │  оркестрация, домен, доступы    │
                    └─┬───────┬────────┬──────┬───────┘
                      │       │        │      │
        ┌─────────────▼─┐ ┌───▼────┐ ┌─▼────┐ │
        │   postgres    │ │ minio  │ │ tts  │ │  silero, RU
        └───────────────┘ └───▲────┘ └──────┘ │
                              │               │
                         ┌────┴───┐    ┌──────▼─────────┐
                         │  asr   │    │  LLM endpoint  │  OpenAI-совместимый
                         │ ffmpeg │    │   (DeepSeek)   │  внешний, ключ в secrets.yaml
                         └────────┘    └────────────────┘
```

| Контейнер | Что внутри | Почему отдельно |
|---|---|---|
| `frontend` | React 19 + TypeScript, dev-сервер Vite | В разработке идёт через `npm run dev`, прокси `/api` на бэкенд |
| `backend` | Spring Boot 4.1, Kotlin, JDK 25 | Весь домен и оркестрация |
| `postgres` | PostgreSQL 17 | — |
| `minio` | S3 API | Видео, аудио ответов, аудио вопросов |
| `asr` | Python + FastAPI + ffmpeg + faster-whisper | Тяжёлые ML-зависимости не тащим в JVM. ffmpeg живёт здесь же: нормализация в wav 16 kHz нужна только ASR. Две сборки: CPU (`small`) и GPU (`medium`, Р-23) |
| `tts` | Python + FastAPI + Silero | То же — Python-модель |
| LLM | Внешний OpenAI-совместимый endpoint | Сейчас DeepSeek (`deepseek-v4-flash`). Провайдер меняется тремя настройками, ключ в `secrets.yaml` вне репозитория (Р-5) |

Браузер ходит в MinIO напрямую по presigned URL — и на запись чанков, и на
чтение видео в карточке. Через backend медиа не гоняем.

**Решено (Р-17).** nginx проксирует `/s3/*` в MinIO, backend подписывает URL с
публичным базовым адресом `http://localhost/s3`. Через JVM медиа не идёт.

## 2. Модули бэкенда

Один Gradle-модуль, границы — пакетами. Домен не знает про Spring.

```
com.itmo.napoleonit.aiinterviewer
├─ config/          настройки, Spring Security, OpenAPI
├─ domain/          строки таблиц и стейт-машины. Без Spring
├─ persistence/     репозитории на JdbcClient, конвертеры jsonb
├─ service/         оркестрация: вакансии, интервью, сессия кандидата, пайплайн ответа
├─ questions/       QuestionGenerator, FollowUpGenerator + реализации
├─ transcription/   AsrEngine, TranscriptRefiner
├─ evaluation/      рубрика, оценка ответа, сборка карточки, текст выводов
├─ llm/             OpenAI-совместимый клиент, изоляция недоверенного текста
├─ tts/             TtsEngine
├─ media/           S3, presigned URL
├─ data/            эталонные данные заказчика: вакансия и 6 вопросов
└─ web/             REST-контроллеры, DTO, обработка ошибок
```

Правило зависимостей: `web` → сервисы → `domain`. Обратных стрелок нет.
`llm` не знает про интервью, `questions`/`evaluation` не знают про HTTP.

Все внешние ML-вызовы за интерфейсами (`AsrEngine`, `TtsEngine`, `LlmClient`,
`QuestionGenerator`, `FollowUpGenerator`) — требование Р-7, Р-8 и обещание
заказчику про сменяемость моделей (`[8:17]`).

## 3. Стейт-машины

Это ядро корректности. Оба статуса видны в UI — Рамка §7 требует показывать
состояние обработки.

### Интервью

```
CREATED ──consent──► READY ──start──► IN_PROGRESS ──все ответы──► ANALYZING
                                           │                          │
                                           │                          ├─► READY_REPORT
                                        EXPIRED                       └─► FAILED
```

- `CREATED` → `READY`: кандидат поставил чекбокс согласия (Р-3), прошёл проверку
  камеры и микрофона.
- `IN_PROGRESS`: есть текущий вопрос. Возврат по ссылке после потери сети
  возобновляет с него же.
- `ANALYZING`: последний ответ обработан, собирается карточка.
- `EXPIRED`: истёк TTL ссылки.

### Ответ

Маппится на статусы Рамки §7 один в один:

```
RECORDING ──► UPLOADED ──► TRANSCRIBING ──► EVALUATING ──► EVALUATED
     │                          │                │
     │                          │                └──────► FAILED
     │                          │
     │                          └──────► UNRATEABLE (запись не разобрать)
     │
     └──────► SKIPPED (кандидат пропустил вопрос)
```

`UNRATEABLE` — отдельно от `FAILED`. Это не сбой системы, а честный вывод
«ответ невозможно уверенно оценить» (Рамка §7 и §8, п.6). В карточку попадает
как «не удалось оценить», а не как низкий балл.

Начиная с `EVALUATING` ответ считается **settled**: кандидат с ним закончил и
получил следующий вопрос, хотя оценка ещё считается. Прогресс кандидата
показывается по `settled`, а интервью закрывается по терминальным состояниям —
иначе карточка собиралась бы раньше, чем готовы оценки.

## 4. Поток прохождения интервью

Ключевая развилка — что происходит между ответом и следующим вопросом.
Кандидат в этот момент ждёт, поэтому синхронно делается только то, без чего
нельзя показать следующий вопрос.

```
кандидат записал ответ
   │
   ├─► один PUT blob на presigned URL (Р-17)
   │
   └─► POST /answers/{id}/complete
          │
          backend ставит job, отвечает сразу 202
          │
       фронт поллит GET /api/s/{token} раз в секунду (Р-18)
          │
    ┌─────┴──────────────── синхронно, кандидат ждёт ────────────────┐
    │  ffmpeg → wav ──► ASR ──► выравнивание техжаргона              │
    │                              │                                 │
    │                    FollowUpGenerator.decide()                  │
    │                              │                                 │
    │               ┌──────────────┴──────────────┐                  │
    │            Ask(уточнение)              Proceed                  │
    │               │                             │                  │
    │               └──────────► next question ◄──┘                  │
    └────────────────────────────────────────────────────────────────┘
          │
          └─► в фоне: оценка ответа по рубрике ──► сохранение
                             │
                   последний ответ оценён ──► сборка карточки
```

**Оценка ответа вынесена в фон.** Кандидату она не нужна — нужна карточке.
Пока она считалась синхронно, пауза между вопросами доходила до 26 секунд;
после разделения — 2–13 секунд при том же качестве разбора. Прогресс кандидата
считается по состоянию `settled`, чтобы не зависеть от скорости модели.

Интервью закрывается, когда оценён последний ответ, а не когда кандидат
отправил последнюю запись: иначе карточка собиралась бы по неполным данным.

Асинхронность: пул воркеров + таблица `processing_job` для видимости статуса.
Никаких Kafka и очередей — на одну машину и десяток интервью это оверинжиниринг,
а заказчик просил фокус на качестве оценки, не на инфраструктуре.

## 5. Модель данных

Flyway, `V1__init.sql`. Spring Data JDBC: агрегаты явные, между агрегатами —
ссылки по id (`AggregateReference`), не объектные графы.

```
vacancy ──1:N── requirement
   │
   └──1:N── question_set (иммутабельный, версионированный)
                 └──1:N── question          ← только обязательное ядро

interview ──► vacancy, question_set (снапшот-ссылка)
   │
   ├──1:N── interview_question   ← фактический план: CORE + PERSONAL + FOLLOWUP
   │            └──0:1── answer
   │                       ├──0:1── transcript
   │                       └──0:1── answer_evaluation
   ├──1:N── antifraud_event
   ├──1:N── share_link
   └──0:1── report
```

### Почему план интервью снапшотится

`interview_question` — копия текста вопроса, а не ссылка на `question`.
Причина — Р-13: карточка обязана показывать ровно то, что кандидат видел,
даже если рекрутер потом переписал ядро. `question_set` при этом остаётся
якорем сопоставимости: у всех кандидатов одной версии набора одинаковое ядро.

### Таблицы

| Таблица | Ключевые поля |
|---|---|
| `vacancy` | `title`, `grade`, `description` |
| `requirement` | `vacancy_id`, `text`, `kind` MUST/NICE, `weight`, `is_stop_factor`, `not_verifiable_here` |
| `question_set` | `vacancy_id`, `version`, `frozen_at` |
| `question` | `question_set_id`, `ord`, `text`, `requirement_id`, `strong_signals`, `origin`, `tts_key` |
| `interview` | `vacancy_id`, `question_set_id`, `candidate_name`, `resume_text`, `status`, `consent_at`, `expires_at` |
| `interview_question` | `interview_id`, `ord`, `source` CORE/PERSONAL/FOLLOWUP, `origin_question_id`, `parent_answer_id`, `text`, `requirement_id`, `strong_signals`, `origin`, `tts_key` |
| `answer` | `interview_question_id`, `media_key`, `duration_ms`, `status` |
| `transcript` | `answer_id`, `raw_text`, `refined_text`, `segments` jsonb, `asr_model` |
| `answer_evaluation` | `answer_id`, `scores` jsonb, `quotes` jsonb, `confidence`, `model`, `prompt_version` |
| `report` | `interview_id`, `recommendation`, `overall_score`, `confidence`, `payload` jsonb, `model`, `prompt_version`, `rubric_version` |
| `antifraud_event` | `interview_id`, `type`, `occurred_at` |
| `share_link` | `interview_id`, `role`, `token`, `expires_at`, `revoked_at` |
| `processing_job` | `answer_id`, `kind`, `state`, `attempts`, `last_error` |

`requirement.not_verifiable_here` — из Рамки §3: вакансия должна нести список
навыков, которые этим интервью проверить нельзя. Они уходят в карточку как
«непроверенные», а не как «отсутствующие».

`transcript` хранит **и сырой, и выправленный** текст — Рамка §7 запрещает
незаметно менять историю результата правкой транскрипта.

Версионирование модели и промптов лежит на `answer_evaluation` и `report`
(Рамка §10).

**Решено (Р-19).** jsonb + ручные конвертеры Spring Data JDBC.

## 6. Доступ

Три пути, разные механизмы.

| Кто | Как входит | Что видит |
|---|---|---|
| Рекрутер | Логин | Все свои вакансии и всех кандидатов по ним |
| Кандидат | Токен в ссылке интервью, одноразовое назначение, TTL | Только свою сессию |
| Нанимающий менеджер | Токен в ссылке результата, TTL, отзываемый | Только один конкретный отчёт, read-only |

Разграничение — жёсткое требование Рамки §10 и критерий готовности «Защита
данных». Нанимающий менеджер физически не может получить список кандидатов:
у его токена нет ничего, кроме одного `interview_id`.

**Решено (Р-20).** Spring Security, form login, сессия в куке, пользователи
в памяти. Больше ничего.

## 7. API

Полный контракт — `docs/api.md`, живая спецификация — Swagger UI на
`/swagger-ui.html`. Здесь только принцип разбиения.

Три семейства путей, разграничение читается прямо в роутинге:

| Префикс | Кто | Как аутентифицируется |
|---|---|---|
| `/api/...` | рекрутер | сессионная кука |
| `/api/s/{token}/...` | кандидат | токен сессии интервью |
| `/api/r/{token}` | нанимающий менеджер | токен ссылки на результат |

Разные префиксы выбраны не для красоты: разграничение доступа должно быть
видно в адресе, а не прятаться в проверках внутри контроллеров. В Swagger они
разложены по трём группам по той же причине.

## 8. Внутренние сервисы

```
POST  asr:8000/transcribe   { media_url }
                         -> { text, segments[{start_ms, end_ms, text}], model,
                              usable, duration_ms }
POST  tts:8000/synthesize   { text } -> audio/wav
GET   asr|tts:8000/health   -> { status, ... }
```

Наружу они торчат как `8100` и `8101`. Поле `usable` — способ ASR сказать
«записи не хватило на осмысленный текст»: ответ тогда получает `UNRATEABLE`,
а не низкий балл.

`asr` сам скачивает объект из MinIO по presigned URL и сам гоняет ffmpeg —
backend не занимается медиа-конвертацией. Ссылка подписывается на **внутренний**
адрес сети compose: подпись привязана к хосту, и ссылка для браузера в
контейнере не сработает.

`tts` вызывается лениво, с кэшем в S3 по хешу текста (Р-22): одинаковые вопросы
делят одно аудио.

Оба клиента ходят по HTTP/1.1 намеренно. JDK-клиент пробует апгрейд до h2c,
uvicorn его не понимает и теряет тело запроса — сервис отвечал 422.

Таймкоды из `segments` нужны обязательно: Рамка §8 требует подтверждать выводы
цитатой **и таймкодом**, а карточка должна уметь перематывать видео на момент
цитаты. Это заметная часть «объяснимости», ради которой весь кейс.

## 9. Что построено

Порядок был взят из демо-сценария Рамки §15: сначала сквозной тонкий путь,
потом качество. Все шаги пройдены.

| Шаг | Состояние |
|---|---|
| compose, миграции, S3, API | готово, 25 путей, Swagger на `/swagger-ui.html` |
| Вакансия, требования, эталонные вопросы | готово |
| Прохождение: MediaRecorder → S3 | готово, экран в виде видеозвонка |
| Распознавание и выравнивание техжаргона | готово, faster-whisper, на GPU 19× реального времени |
| Оценка ответа и карточка | готово, вердикты правилами, текст моделью |
| Генерация вопросов моделью | готово, ядро и персональные по резюме |
| Адаптивные уточнения | готово, Р-1 и Р-25 |
| Озвучка, доступы, версионирование, устойчивость | готово |
| Фидбэк кандидату, антифрод | готово, плюс защита от внедрения в промпт (Р-24) |

Не сделано и сделано не будет в рамках MVP: ранжирование кандидатов (Р-2),
интеграции с ATS и почтой, live-coding. Не измерено: метрика 80% совпадений
с экспертом (Р-9) — нет размеченной выборки.

## 10. Риски и чем закончились

| Риск | Чем закончился |
|---|---|
| ASR плохо берёт RU-техжаргон | Подтвердился: «кафку» → «кавку», «дедупликация» → «дубликация». Закрыт словарным рефайнером, словарь набран по реальным ошибкам, а не по догадкам |
| Модель не держит structured output | Подтвердился: DeepSeek не поддерживает `json_schema`. Клиент сам понижается до `json_object` и запоминает выбор |
| Кодеки `MediaRecorder` разошлись между браузерами | Открыт (О-11). Нормализация ffmpeg на стороне `asr` снимает большую часть, Safari не проверялся |
| Ожидание между вопросами слишком длинное | Подтвердился: 26 секунд. Закрыт разделением пайплайна и настройкой глубины рассуждений — стало 2–13 секунд |
| Нет выборки для метрики 80% | Открыт. Показываем методику, а не число (Р-9) |
| Кандидат обращается к модели через резюме или ответ | Закрыт четырьмя слоями (Р-24), проверен живой атакой |
| Уход кандидата в другое окно не фиксируется | Подтвердился на нескольких мониторах: `document.hidden` не меняется. Закрыт отслеживанием фокуса окна |

## 11. Чего стоит опасаться дальше

Не риски реализации, а свойства решения, о которых честно стоит помнить.

- **Данные кандидатов уходят во внешний API.** Заказчик вопрос про зарубежные
  модели и реестр ПО отложил (созвон `[7:56]`). Переезд стоит правки трёх
  настроек, но решение принимать ему.
- **Защита от внедрения в промпт снижает вероятность, а не исключает.** Модель
  принципиально не отличает данные от инструкций, поэтому событие
  `PROMPT_INJECTION` — сигнал человеку, а не приговор.
- **Антифрод обходится.** Второй экран виден только в Chromium, фокус окна
  можно не терять, а подсказку держать на телефоне. Это осознанно: заказчик
  сам сказал, что исключить обман нельзя ни вживую, ни с ИИ (`[25:46]`).
- **Качество оценки не измерено.** Пока это утверждение, а не факт: сравнения
  с экспертом на размеченной выборке не было.
