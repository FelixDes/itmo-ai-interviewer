# AI-интервьюер — пользовательские сценарии

Статус: предложение v1, 2026-09-03.

Это **MVP**. Принцип отбора экранов: экран попадает в скоуп, только если он
нужен для сквозного демо-сценария (Рамка §15) или закрывает критерий готовности
(Рамка §13). Всё остальное — в §6 «Чего в интерфейсе нет».

Термин «интервьюер» в этом документе = **рекрутер**. Живого интервьюера в
продукте нет, его роль заменяет система.

## 1. Карта экранов

```
РЕКРУТЕР                                   КАНДИДАТ
                                           
R1 Логин                                   C1 Приветствие + согласие
  └► R2 Список вакансий                      └► C2 Проверка камеры и микрофона
       ├► R3 Вакансия: описание,                  └► C3 Вопрос и запись ответа ◄─┐
       │    требования, веса                          └► C4 Обработка ──────────┘
       │    └► R4 Вопросы: ядро                            └► C5 Завершение
       └► R5 Кандидаты вакансии
            ├► R6 Новое интервью → ссылка   НАНИМАЮЩИЙ МЕНЕДЖЕР
            └► R7 Карточка результата       M1 Карточка результата (read-only)
```

Девять экранов на всё. R7 и M1 — один компонент с разным набором действий.

## 2. Сценарий рекрутера

### R1. Логин

Форма, seed-пользователи. Существует только чтобы разграничение доступа было
настоящим, а не нарисованным (критерий «Защита данных»).

### R2. Список вакансий

Таблица: название, грейд, число кандидатов, кнопка «Создать вакансию».
Без фильтров и поиска — на демо вакансий две.

### R3. Вакансия

Поля: название, грейд, описание роли.

Требования — список строк, у каждой:

| Поле | Значения |
|---|---|
| Текст | «Apache Kafka — продакшн-опыт с producers/consumers» |
| Тип | **обязательное** / желательное |
| Вес | 1–3 |
| Стоп-фактор | да / нет |
| Не проверяется этим интервью | да / нет |

Тип и вес нужны, потому что Рамка §8 требует оценивать обязательные и желательные
навыки **раздельно**. «Не проверяется» — из Рамки §3: такие навыки уходят в
карточку как «непроверенные», а не как «отсутствующие».

Для демо требования подставляются из `Пример вакансии и вопросов.pdf`.

### R4. Вопросы (обязательное ядро)

Кнопка «Сгенерировать вопросы» → LLM отдаёт 5–7 вопросов. У каждого видно:

- текст вопроса;
- какое требование он проверяет;
- признаки сильного ответа;
- основание генерации (вакансия / резюме / предыдущий ответ).

Рекрутер правит текст, удаляет лишнее, добавляет своё. Кнопка «Зафиксировать» →
создаётся новая версия `question_set`, для неё пакетно генерится TTS-аудио.

Правка после фиксации создаёт **новую версию** (Р-13). Уже прошедшие кандидаты
остаются на своей — иначе ломается сопоставимость.

На экране есть переключатель источника: «сгенерировать LLM» / «взять эталонные
6 вопросов» (Р-14). Второе — для отладки оценки и для демонстрации сравнения
с эталоном заказчика.

### R5. Кандидаты вакансии

Таблица: имя, статус интервью, дата, итоговая рекомендация.

Статусы человеческим языком: `ссылка выдана` → `интервью идёт` → `обрабатывается`
→ `готово` / `ошибка` / `ссылка истекла`.

Сортировки по баллу и рейтинга **нет** — Р-2, ранжирование вне скоупа.

### R6. Новое интервью

Форма: имя кандидата, резюме текстом (Р-11, поле-textarea, опционально).

По кнопке система:
1. привязывает интервью к активной версии `question_set`;
2. копирует ядро в план интервью;
3. генерирует персональные вопросы по резюме и дописывает их в план (Р-12, без
   участия рекрутера);
4. отдаёт ссылку для кандидата.

Рекрутер копирует ссылку и сам шлёт её кандидату в мессенджер или почту — ровно
как сейчас шлёт ссылку на Zoom (созвон `[9:40]`). Автоотправки нет, она вне скоупа.

### R7. Карточка результата

Главный экран продукта. На нём защищается вся работа, поэтому расписан подробно.

**Шапка**
- итоговая рекомендация: `подходит` / `не подходит` / `требуется дополнительная проверка`;
- общий балл;
- уверенность модели;
- одноабзацное объяснение решения.

**Соответствие требованиям**

Таблица по требованиям вакансии, обязательные и желательные — **раздельными
блоками**. По каждому: оценка, откуда вывод (ответ / резюме / не проверено),
ссылка на подтверждающую цитату.

**Разбор по вопросам**

Для каждого вопроса — раскрывающийся блок:
- текст вопроса и что он проверял;
- видеоответ (плеер);
- транскрипт; переключатель «выправленный / сырой» (Рамка §7: правка транскрипта
  не должна незаметно менять историю результата);
- оценки по рубрике: техническая корректность, глубина, релевантность, наличие
  примера, личный вклад, масштаб и метрики, уверенность;
- цитаты с таймкодами — клик перематывает видео на момент.

Помечен ли вопрос как персональный или уточняющий — видно тут же, вместе с
основанием генерации.

**Выводы**
- сильные стороны с подтверждающими цитатами;
- риски, противоречия, зоны роста;
- выявленные навыки;
- **непроверенные** навыки — отдельным списком, это не то же самое, что отсутствующие;
- вопросы, которые рекомендуется задать на следующем этапе.

Каждый существенный вывод помечен типом: **факт** / **вывод модели** /
**предположение** (Рамка §8 п.4). Это не украшение — это ровно то, чем наша
карточка отличается от «ИИ что-то написал».

**Технический блок** — отдельно, ниже, визуально отделён от профессиональной оценки:
- антифрод-события, если включены (уход из вкладки, вставка текста);
- сбои обработки, ответы со статусом «не удалось оценить».

Рамка §11 прямо запрещает смешивать антифрод с профессиональным баллом.

**Действия**
- «Скопировать обратную связь для кандидата» — готовый текст (Р-4), отправляет рекрутер сам;
- «Выдать ссылку нанимающему менеджеру» → токен с TTL;
- «Отозвать ссылку».

## 3. Сценарий кандидата

Кандидат не логинится. Вся сессия живёт по токену из ссылки.

### C1. Приветствие и согласие

Видит: название вакансии, компанию, число вопросов, ожидаемую длительность,
правила прохождения (одна попытка на вопрос, назад вернуться нельзя, ведётся
запись видео и звука).

Чекбокс согласия на запись и обработку — с текстом-плейсхолдером (Р-3).
Без отметки «Начать» не активна. Факт и время согласия пишутся в БД.

Если антифрод включён — здесь же предупреждение, что фиксируются уход со
вкладки и вставка текста. Рамка §11 требует предупреждать.

### C2. Проверка камеры и микрофона

Превью с камеры, индикатор уровня звука, тестовая запись на несколько секунд с
воспроизведением. Кнопка «Всё работает, начать интервью».

Если доступ к камере запрещён — понятная инструкция, как выдать разрешение,
и повтор проверки. Дальше не пускаем: интервью без видео бессмысленно (созвон
`[2:41]` — видео именно против подставных лиц).

### C3. Вопрос и запись ответа

Экран сделан похожим на видеозвонок: тёмный фон, две плитки участников,
панель управления снизу. Кандидату это привычнее, чем веб-форма с кнопками,
а поведение остаётся асинхронным.

- плитка интервьюера с аватаром, который «оживает», пока звучит вопрос;
- плитка кандидата с собственным видео и меткой «запись» в углу;
- вопрос под плитками, как субтитры; кнопка «прослушать заново»;
- кнопка ответа круглая и строго по центру нижней панели;
- слева таймер во время записи, справа «Пропустить».

**Счётчика «вопрос 3 из 7» нет намеренно.** План растёт по ходу интервью за счёт
уточняющих вопросов, и счётчик прыгал бы: «3 из 8», потом «4 из 9». Это выглядит
как сбой и подталкивает кандидата отвечать короче, чтобы «быстрее закончить».
В живом интервью человек тоже не знает, сколько вопросов осталось.

Запись стартует по кнопке кандидата, а не автоматически — дать секунду собраться.

Чанки видео уходят в S3 **во время** записи. Это не оптимизация ради галочки:
за счёт этого пауза после ответа сокращается на его длительность, а при обрыве
сети не теряется весь ответ.

Пропуск — осознанное действие с подтверждением. Ответ сохраняется как
«не отвечено» и в карточке даёт «не удалось оценить», а не низкий балл.

### C4. Обработка

После «Завершить ответ» — экран ожидания с честным статусом: `сохраняем` →
`расшифровываем` → `готовим следующий вопрос`.

Дальше система либо задаёт **уточняющий вопрос** (Р-1: ответ был общим, без
примера, без личного вклада, без масштаба, или противоречит резюме), либо идёт
к следующему вопросу плана. Кандидат не знает заранее, какой из двух — и это
нормально.

При ошибке генерации уточнения интервью **молча продолжается** по базовому плану
(требование Рамки §5). Кандидат сбоя не видит.

### C5. Завершение

Подтверждение, что интервью отправлено, и что результат уйдёт рекрутеру.
Повторный вход по той же ссылке показывает этот же экран — переигрывать нельзя.

## 4. Сценарий нанимающего менеджера

Одна ссылка → M1 → та же карточка, что R7, но:
- без кнопок «выдать ссылку», «отозвать», «скопировать фидбэк»;
- без выхода в список кандидатов и вакансий — его просто некуда сделать, в токене
  лежит один `interview_id`.

Заказчик описал роль именно так (созвон `[39:07]`): «учётка нанимающего менеджера
— он видит кандидатов только по своей вакансии», и рекрутер сам решает, кого
показать.

## 5. Пограничные случаи

| Ситуация | Поведение |
|---|---|
| Потеря сети во время записи | Чанки докладываются при восстановлении; если ответ не долетел — предложение перезаписать **этот** ответ |
| Закрыл вкладку посреди интервью | Вход по ссылке возвращает на текущий вопрос. Прошлые ответы сохранены |
| Отказал в доступе к камере | Инструкция и повтор проверки. Дальше не пускаем |
| Ссылка истекла | Экран «ссылка недействительна, обратитесь к рекрутеру» |
| Интервью уже пройдено | Экран C5, переигровки нет |
| ASR упал на одном ответе | Ответ → `не удалось оценить`, интервью продолжается, в карточке видно в техническом блоке |
| LLM недоступен во время интервью | Уточнения выключаются, интервью идёт по базовому плану |
| LLM недоступен при сборке карточки | Статус `ошибка`, кнопка «повторить анализ» у рекрутера |

Пункт «Устойчивость» из критериев готовности (Рамка §13) закрывается строками
1, 3 и 6 — их надо уметь показать на демо, а не только реализовать.

## 6. Чего в интерфейсе нет

Сознательные MVP-отсечения:

- рейтинг, сортировка и сравнение кандидатов (Р-2);
- редактирование транскрипта рекрутером — только просмотр сырого и выправленного;
- отправка писем, приглашений, напоминаний;
- дашборды и аналитика по вакансии;
- регистрация кандидатов, личный кабинет кандидата;
- отправка обратной связи кандидату из системы — текст генерим, шлёт рекрутер руками;
- мобильная вёрстка кабинета рекрутера. Экран кандидата адаптивный, кабинет — desktop-only.

## 7. Предлагаемые лимиты

Закрывает О-6, Рамка §6 оставляет эти числа на нас.

| Параметр | Значение |
|---|---|
| Вопросов в ядре | 5–7 |
| Уточнений на один ответ | не более 2, решает система |
| Всего вопросов в интервью | не более 12 |
| Времени на ответ | до 5 минут, мягкий таймер |
| Попыток на вопрос | одна, перезапись только при сбое загрузки |
| Пауза | нет |
| Пропуск вопроса | есть, с подтверждением |
| TTL ссылки кандидата | 7 дней |
| TTL ссылки на результат | 30 дней, отзывается вручную |
| Ожидаемая длительность интервью | 20–30 минут |

Одна попытка — потому что интервью должно оставаться оценкой, а не черновиком.
Пропуск оставлен, иначе кандидат застревает на вопросе не по своей специализации.
