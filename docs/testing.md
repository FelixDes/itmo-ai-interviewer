# Как протестировать систему

## 1. Поднять стек

```bash
docker compose up -d                 # postgres, minio, asr, tts
./gradlew bootRun                    # бэкенд на 8080
cd frontend && npm install && npm run dev   # фронт на 5173
```

С видеокартой NVIDIA распознавание идёт примерно в двадцать раз быстрее:

```bash
docker compose -f docker-compose.yml -f docker-compose.gpu.yml up -d --build asr
```

Проверить, что всё живо:

```bash
curl -s localhost:8080/actuator/health | python3 -m json.tool
curl -s localhost:8100/health          # распознавание речи
curl -s localhost:8101/health          # озвучка
```

В `actuator/health` есть компонент `llm`: там видно, какая модель отвечает и
отвечает ли вообще. Статус всегда `UP` — отсутствие модели не поломка, система
штатно переходит на правила.

## 2. Автоматическая проверка

```bash
python3 scripts/smoke.py             # всё целиком, около двух минут
python3 scripts/smoke.py api         # только API, доступы и коды ошибок
```

Зависимостей нет, только стандартная библиотека. Скрипт проходит систему тем же
путём, что и живой пользователь: заводит вакансию, создаёт интервью, отвечает на
все вопросы синтезированной речью, дожидается карточки и проверяет разграничение
доступа.

Проверяется в том числе то, что легко сломать незаметно:

| Что | Почему это важно |
|---|---|
| Правка зафиксированного набора отбивается `409` | Иначе карточки прошедших кандидатов начнут ссылаться на вопросы, которых те не видели |
| Сырой и выправленный транскрипт хранятся оба | Правка расшифровки не должна незаметно менять историю результата |
| У цитат есть таймкоды | На них держится проверяемость выводов |
| Непроверенное отделено от отсутствующего | «Не спрашивали» и «не умеет» — разные вещи |
| Часть критериев остаётся без оценки | Когда судить нельзя, это `null`, а не ноль |
| Менеджер по ссылке не видит список кандидатов | Разграничение доступа |

Юнит-тесты бэкенда:

```bash
./gradlew test
```

Отдельно покрыт рефайнер техжаргона — место, где регулярка легко ломает
соседние слова. Тесты написаны на реальных ошибках распознавания.

## 3. Ручная проверка в браузере

Автоматика не проверяет камеру, микрофон и кодеки записи: для этого нужен живой
браузер с разрешениями. Это единственная часть, которую надо пройти руками.

**Рекрутер.** Откройте http://localhost:5173, войдите как `recruiter` / `recruiter`.

1. «Демо-вакансия» — появится Middle+ Python с 18 требованиями и эталонными
   вопросами.
2. «Сгенерировать моделью» — вопросы напишет LLM. Занимает до минуты.
   Проверьте, что каждый привязан к требованию и что у него есть признаки
   сильного ответа.
3. Правьте вопросы, нажмите «Зафиксировать». Попробуйте изменить их снова —
   интерфейс предложит создать новую версию, а не молча перезапишет.
4. «Кандидаты» → создайте интервью, вставив текст резюме. Скопируйте ссылку.

**Кандидат.** Откройте ссылку, лучше в отдельном окне.

1. Прочитайте правила, отметьте согласие.
2. Проверка камеры: должно появиться изображение и шевелиться индикатор звука.
3. Отвечайте на вопросы вслух. После ответа — экран ожидания со стадиями
   обработки.
4. Где-то на втором-третьем ответе система задаст уточняющий вопрос, если
   ответ был общим. Это и есть адаптивность.
5. Один вопрос пропустите — он попадёт в карточку как непроверенная компетенция.

**Результат.** Вернитесь в кабинет рекрутера, откройте карточку.

- Клик по цитате перематывает видео на нужный момент.
- Переключатель «сырая / выправленная» показывает, что сделал рефайнер.
- Обязательные и желательные требования — разными таблицами.
- «Ссылка нанимающему» → откройте её в приватном окне: отчёт виден, а списка
  кандидатов нет. Отзовите ссылку и обновите страницу.

## 4. Что стоит сломать намеренно

Устойчивость — отдельный критерий готовности, и её надо уметь показать.

| Действие | Ожидаемое поведение |
|---|---|
| Запретить доступ к камере | Понятная инструкция, дальше не пускает |
| Закрыть вкладку посреди интервью | Вход по той же ссылке возвращает на текущий вопрос |
| `docker compose stop asr` | Интервью идёт, расшифровка от заглушки, в логе одно предупреждение |
| `docker compose stop tts` | Вопрос показывается текстом, озвучка — тишина |
| Убрать ключ из `secrets.yaml` | Вопросы берутся эталонные, оценка считается правилами, карточка помечает это в техническом блоке |
| Открыть ссылку кандидата после завершения | Экран «интервью отправлено», переигровки нет |

Ни один из этих случаев не должен ронять интервью — в этом и была идея
запасных путей у каждого внешнего сервиса.

## 5. Качество оценки

Главная метрика кейса — совпадение вывода системы с оценкой эксперта не менее
чем в 80% случаев по трём классам. Сейчас она не измеряется: экспертная оценка
есть ровно на одного кандидата, реальных записей интервью заказчик не даёт.

Что можно сделать уже сейчас:

1. Прогнать эталонный набор из 6 вопросов (кнопка «Эталонные 6») и сравнить
   карточку с `Пример_детализации_и_анализа_видео_интервью.pdf`.
2. Отвечать намеренно по-разному — с цифрами и без, со своим вкладом и «мы в
   команде» — и смотреть, различает ли это оценка. В прогонах различает:
   ответы с числами дают `CONFIRMED`, «не помню» оставляет критерии без оценки.

## 6. Если что-то не работает

```bash
docker compose logs asr --tail 50     # распознавание
docker compose logs tts --tail 50     # озвучка
tail -50 nohup.out                    # бэкенд, если запущен через nohup
```

Частое:

- **Порт 5432 занят** — постгрес проекта слушает 5433, это норма.
- **MinIO отказывается принимать запись** — кончилось место на диске.
- **Первая сборка `asr` и `tts` идёт долго** — в образы кладутся модели, чтобы
  на демо не зависеть от интернета.
- **Ответы кандидата не распознаются** — проверьте, что `asr` видит MinIO:
  ссылка подписывается на внутренний адрес сети compose, а не на `localhost`.
